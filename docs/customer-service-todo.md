# 智能客服落地待办

更新日期：2026-10-29。

首版目标：在一个服务入口，为一类明确的客户提供知识咨询、必要的只读业务查询和人工转接。先完成内部试点，再开放给真实客户。以下状态按当前代码与本地验证填写，不代表已完成生产部署。

- [x] 客服、知识问答、聊天预设，以及可扩展的回答策略。
- [x] 会话、事件、知识库与长期记忆的基础存储接口和租户范围约束。

- [x] Ops 独立监听与凭证；运行排查与插件管理分开授权。
- [x] Ops 运行列表、执行轨迹、节点详情与错误定位。
- [x] 插件 ZIP 上传、静态校验、未启用登记、版本保留及启用失败回退。
- [x] 10 篇虚构客服资料及 20 个评测问题；已验证资料格式、临时导入、检索和租户隔离。

资料入口：[演示知识库](../examples/customer-service-knowledge/README.md)、[插件上传](plugin-upload.md)、[个人身份配置](personal-access.md)。

## P0：内部试点前完成

### 1. 确定业务范围和真实资料负责人

- [ ] 明确首批服务对象、入口及前三类高频问题，列出不处理的业务。
- [ ] 指定知识、售后政策和人工服务的负责人。
- [ ] 将虚构演示资料替换为审核过的产品资料、FAQ、售后政策和处理流程。
- [ ] 配置有效的人工服务入口、服务时间和处理责任人，不把演示时效当作企业承诺。

验收：每项对外政策都有明确来源、适用产品和维护负责人；客户遇到无法解决的问题有可执行的后续途径。

### 2. 接入真实主模型和 Embedding

- [ ] 配置主模型的 LLM_BASE_URL、LLM_API_KEY、LLM_MODEL，验证中文问答、结构化决策和取消行为。
- [ ] 配置 Embedding 的地址、密钥、模型及 EMBEDDING_DIMENSIONS，验证输出维度和中文检索。
- [ ] 恢复默认或正式客服 Decision Provider；固定追问的上传示例只用于测试插件安装。
- [ ] 明确超时和失败时的客户提示，不把 Provider 原始错误或凭据返回给用户。

验收：真实模型能根据检索证据回答、追问或拒答；没有证据时不编造答案、工具结果或联系方式。

说明：首版需要主语言模型和 Embedding 两类模型。现有主模型可同时完成决策与回答，不必先增加独立路由、意图分类或摘要模型。

### 3. 准备持久化基础设施并导入知识

- [ ] 准备 PostgreSQL、Redis、Qdrant 和生产凭据，执行数据库迁移；开发 Compose 不直接视为生产配置。
- [ ] APP_MODE 切换为 live，确认没有回退到 mock 或内存存储。
- [ ] 创建与真实 Embedding 维度匹配的向量集合，避免复用 64 维 mock 集合；重新生成知识向量。
- [ ] 按目标租户导入审核资料，核对聊天身份、导入管理员与知识所属租户。
- [ ] 重启服务后验证会话、知识、插件状态和已上传插件文件仍可用。

验收：使用真实基础设施完成一次知识导入、检索、回答和轨迹查询，重启后数据可恢复。密钥不进入 Git 或共享排障输出。

### 4. 做业务评测

- [ ] 先运行已有 20 个演示评测问题，再补真实历史咨询、信息不足、资料冲突、越权和接口失败用例。
- [ ] 分别检查检索是否找对资料、答案是否受资料支持、工具是否正确使用、是否正确转人工。
- [ ] 记录回答质量、响应时间、token 用量与处理成本，由业务负责人确定可接受标准。
- [ ] 将错误承诺、越权泄露、虚构执行成功和危险操作指导作为阻断上线的问题。

验收：业务负责人审查关键用例并确认试点范围；每个失败用例能关联到 runId 进行排查。现有 Guard 只验证引用真实性及配置策略，不保证逐句事实正确。

### 5. 建立人工处理闭环

- [ ] 客户明确要求人工、安全风险、证据不足或业务结果不确定时，提供人工处理路径。
- [ ] 首版可以使用人工留言或工单；接入真实系统后再展示工单号和处理状态。
- [ ] 交接包含已核实事实、待核实信息、已执行步骤和必要的工具结果，并过滤敏感信息。
- [ ] 只有工具明确成功才告知“已创建工单”或“已接入人工”；没有坐席系统时不显示虚构排队人数和等待时间。

验收：从客户发起转人工到人工拿到上下文，至少完成一次端到端演练。

## P1：对应能力开放前完成

### 6. 知识更新与敏感资料权限

- [ ] 增加文档有效版本、撤回和旧版下线机制，避免新旧政策同时参与默认检索。
- [ ] 在导入 HR、财务等敏感资料前，将可信用户身份传入知识查询，并由服务端强制执行文档可见范围。
- [ ] 验证跨用户、跨部门及跨租户的拒绝访问用例；metadata.department 和模型筛选参数不能替代授权。

验收：旧政策撤回后不再进入新回答；无权用户无法通过改变问题或 filters 检索受限文档。

### 7. 真实业务查询与写操作

- [ ] 接入订单、物流、保修等真实只读工具，每次校验业务对象是否属于当前用户。
- [ ] 开放写操作前，修正“副作用已完成，但返回过大或结果处理失败被记为普通失败”的状态分类。
- [ ] 为创建工单、取消订单、退款等操作设置业务幂等键、客户确认、必要审批和结果核对。
- [ ] 结果不确定时停止自动重复提交，保留轨迹并交人工核查。

验收：重复请求、超时、审计失败和结果处理失败均不会造成重复办理；没有成功证据时不向客户报告完成。

### 8. 正式客户身份

- [ ] 内部试点按人分配独立 Token 和 userId；同公司共享 tenantId，不共享个人凭据。
- [ ] 面向正式客户时，接入公司已有登录或客户会话系统，映射为服务端 Principal。
- [ ] 增加账号停用、会话过期和撤销，并明确多租户成员关系及切换规则。
- [ ] 继续区分业务访问、只读排障和插件管理权限。

验收：身份切换不显示前一用户数据；停用或撤销后新请求失效；业务身份无法登录 Ops。当前静态 Token 的配置删除与重启只是过渡方案。

### 9. 生产运行保障

- [ ] 为 Redis 增加可控重连并验证短暂故障后的恢复；当前 retryStrategy 返回 null。
- [ ] 增加依赖就绪检查；现有 /health 只表明 HTTP 进程能响应。
- [ ] 设定全局并发、租户用量与费用限额，以及错误率、依赖故障和慢请求告警。
- [ ] 备份数据库、知识数据、插件状态文件及旁边的 packages 目录，验证恢复过程。
- [ ] 定义聊天记录、事件、审计和个人信息的保存、访问与清理规则。

验收：完成依赖重启、备份恢复、限额触发与告警演练；异常时不会持续接收无法完成的业务请求。

## 建议执行顺序

真实资料与人工入口 → 主模型与 Embedding → 持久化导入 → 评测 → 内部试点 → 客户身份与只读业务查询 → 经过确认的业务办理。

每项完成时记录对应提交、验证结果及仍存在的限制。没有真实模型和业务接口验证的任务保持未勾选，不将 mock 演示或代码测试通过等同于生产验收。
